# Benchmark Writeup — Context Compiler

**Status**: final phase (7 of 7). This is a synthesis of results already
produced by Phases 1-6, not new code. Every number below was generated by
the scripts in this repo — see "Reproducing these numbers" at the end.

## What this project set out to test

Per `docs/design.md`: does building an explicit code graph (imports,
calls, class hierarchy, co-change history) and using a *learned, score-guided*
traversal to select context for a coding task do better than a fixed-depth
graph traversal with no learning involved? And does a feedback loop —
retraining the scorer on its own ablation-derived labels — actually
improve it?

## Method, briefly

- **Test repo**: the `ast-graph-transformer` project (this project's own
  earlier deliverable) — a real, if small, Python codebase with genuine
  internal structure (imports, class hierarchies, call chains).
- **Tasks**: 10, auto-generated from the code graph itself (functions/
  methods with ≥2 internal dependencies — see `ablation/tasks.py`), not
  hand-curated. This is a real scope limitation, not a hidden one — see
  Limitations.
- **Ground truth**: a structural dependency-completeness proxy (does the
  selected context include everything the task's target symbol directly
  calls/inherits, per the graph's own edges) — not a real linter or test
  run. See `ablation/proxy_check.py`'s docstring for the full caveat. Every
  precision/recall number below inherits this proxy's narrowness.
- **Token budget**: 2000 tokens per compiled context bundle, for every
  strategy, so comparisons are budget-matched.

## Results

### Compiler quality: fixed-depth baseline vs. score-guided (2 rounds)

| Strategy | Feasible (/10) | Mean precision | Mean recall |
|---|---|---|---|
| Fixed-depth baseline (Phase 2) | 2 | 0.32 | 0.81 |
| Score-guided, round 1 (Phase 5, ~100 training examples) | 2 | 0.24 | 0.65 |
| Score-guided, round 2 (Phase 6, retrained on round-1+round-2 combined) | **4** | 0.31 | 0.78 |

**Reading this honestly**: the learned scorer started out *worse* than
the fixed-depth baseline (expected — round 1 trained on roughly 100
examples, nowhere near enough for a model to generalize). One feedback
iteration closed nearly all of that gap: feasible-task count doubled,
precision and recall both landed within a few points of the baseline.
It did **not** surpass the baseline. The correct claim from this data is
"the feedback loop demonstrably works as a mechanism" — not "learned
beats hand-tuned." Whether more rounds would close the remaining gap,
plateau, or need a stronger proxy check to keep improving is genuinely
unknown from this data; extending the loop further was out of scope for
this project's timeline.

### Token cost by source (compiler-selected vs. agent-pulled)

| Strategy | Mean compiler tokens/task | Mean agent-pulled tokens/task |
|---|---|---|
| Fixed-depth baseline | 1918 | 717 |
| Score-guided, round 1 | 1933 | 558 |
| Score-guided, round 2 | 1957 | 473 |

Compiler token usage is essentially flat across strategies (expected —
all three respect the same 2000-token budget). Agent-pulled tokens trend
downward as the compiler improves — plausible (a better compiler leaves
less for the agent to chase down itself) but **not a verified causal
finding**: the stand-in agent (`ledger/minimal_agent.py`) uses a different
random seed offset per strategy run, which is itself enough to produce
this kind of trend by chance on a 10-task sample. Worth investigating
with matched seeds before treating this as real signal.

## Baselines not built

`design.md` section 4.7 calls for comparison against full-file-dump and
embedding-only-RAG baselines as well, in addition to the fixed-depth-graph
baseline actually built and compared above. Neither full-dump nor
embedding-RAG exist anywhere in this codebase — they were never
implemented, not just left out of this report. Noting that plainly rather
than presenting the fixed-depth comparison as the complete picture
design.md originally asked for.

## Limitations (collected, not rediscovered)

These are pulled from caveats already written into the code and docs
throughout this project — nothing new here, just gathered in one place:

- **The proxy check is structural, not functional** (`ablation/proxy_check.py`).
  Every precision/recall/feasibility number in this report measures
  agreement with the code graph's own direct-dependency edges, not real
  code correctness. A stronger proxy (e.g. pyflakes against a
  reconstructed module) would give an independent signal; this project
  used the cheap structural version throughout, per the 8GB-hardware-driven
  scoping decision made before Phase 4.
- **Tasks are auto-generated, not hand-curated** (`ablation/tasks.py`) —
  a reasonable stand-in for demonstrating the pipeline, not a validated
  benchmark suite.
- **Call/inherit graph edges are name-based, not scope-resolved**
  (`parser/repo_parser.py`) — a known source of noise in the underlying
  graph that every downstream phase inherits.
- **The agent harness is a stand-in** (`ledger/minimal_agent.py`), not a
  real integration (Claude Code, OpenHands, etc.) — its "success" field
  and its tool-call pattern are placeholders, not representative of real
  agent behavior. The token-cost-by-source trend above should be read with
  this in mind especially.
- **Small scale throughout**: one repo, 10 tasks, ~100-200 training
  examples per scorer round. The *direction* of the Phase 6 result (round
  2 beats round 1) is a real, reproducible finding on this repo; the exact
  numbers would differ on a different or larger codebase, and haven't been
  tested on one.
- **One feedback iteration only** — design.md explicitly scoped this to
  avoid iterating to convergence on a portfolio-scale timeline.

## Honest overall framing

This is a working, tested, small-scale system that demonstrates a real
idea end-to-end: a structure-aware code graph, a score-guided compiler
that outperforms nothing yet but is built correctly, an ablation-derived
ground truth (with known limitations), and a feedback loop that measurably
improves the scorer in one iteration. It is not a claim that this beats
production RAG or context-management systems, and the numbers above
shouldn't be read as more than what a 10-task, single-repo, one-iteration
experiment can actually support.

## Reproducing these numbers

```bash
cd scorer
python generate_benchmark_data.py /path/to/ast-graph-transformer \
    ./edge_scorer.pt ./edge_scorer_v2.pt ./benchmark_summary.json
```

Requires both scorer checkpoints already trained (see `README.md`'s
Phase 5/6 sections for how to produce them) and the code graph buildable
from the target repo (Phase 1).
